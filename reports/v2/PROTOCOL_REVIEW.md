# Независимая проверка протокола v2

Статус: проект протокола и рекомендации до нового итогового теста. Это не отчёт об уже проведённом v2-эксперименте. Числа v1 используются только для планирования; результаты v2 здесь не подставляются.

## Главная рекомендация

Использовать **все 9000 пользователей Yambda-50M, не входивших в v1**, с 1000 development-пользователей и 8000 пользователей нового подтверждающего теста. По каждому сохранить все предоставленные исходником события. Основное сравнение — выбранный AutoFE против модели сырых историй с одинаковыми доступными глобальными статистиками. Manual CatBoost остаётся сильным контрольным методом.

Это существенно сильнее простого увеличения `n_users`: будущие ответы новых confirmation-пользователей не используются при подборе, а сами пользователи могут участвовать ранними событиями в обучении. Поэтому проверяется **прогноз будущих откликов знакомых модели пользователей**, а не cold start. V1 и v2 сохраняются как разные исследования.

Оригинальный набор заканчивается на относительном дне 300. Новый тест может быть новым по пользователям и целевым строкам, но не более поздним календарным периодом, чем уже просмотренный тест v1. Это ограничение нельзя исправить одним изменением seed. Данные и временная схема описаны в [оригинальной статье Yambda](https://arxiv.org/html/2505.22238v1).

## 1. Популяция и разделение пользователей

1. Прочитать из исходного sequential parquet только `uid`, а из `reports/main/manifest.json` — 1000 использованных в v1 ID.
2. Проверить уникальность и отсутствие пересечений. Полная новая когорта — дополнение v1 до исходных 10000 пользователей.
3. По фиксированной случайной перестановке новых ID выделить 1000 development и 8000 confirmation. В предложенном `configs/v2.yaml` cohort seed равен `371`, user seed — `20261026`; значения должны попасть в общий lock до чтения новых outcome.
4. Сохранить полные упорядоченные списки ID, контрольные суммы исходных файлов и SHA256 обоих списков в `cohort_lock.json`. Не выбирать пользователей по активности, длине истории, положительной доле или наличию событий в будущем тесте.
5. Сохранить все события каждого нового пользователя. Прореживание допускается только для supervised-дней и контекста нейросети, а не для исходных историй или общего состояния агрегатов.

Не все 8000 confirmation-пользователей обязательно дадут подходящий тестовый запуск. Они не должны заменяться более активными пользователями: фактическое покрытие сообщается после открытия теста.

Рекомендуемые независимые RNG-потоки: разделение пользователей, выбор supervised-дней, контекстный sampling, random-control и bootstrap. Смена seed ради более удобного результата запрещена; все значения фиксируются в конфиге.

## 2. Временная схема и определение задачи

Для преемственности сохранить v1-target: первый за относительный день запуск пары user–item среди **всех** listens, затем фильтр `is_organic == 0`; `label = played_ratio_pct >= 50`. При совпадении timestamp использовать стабильный исходный порядок. Обычные пропуски — реальные отрицательные наблюдения. Не добавлять отрицательные объекты из каталога.

| Период | Относительные дни | Для каких пользователей используются targets |
|---|---|---|
| Разогрев истории | `[0,30)` | Только состояние истории |
| Train | `[30,210)` | Все 9000 новых пользователей |
| Tune | `[210,240)` | Только 1000 development |
| Select | `[240,270)` | Только 1000 development |
| Confirmation | `[270,301)` | Только 8000 confirmation |

Фиксированные числа supervised-дней на пользователя должны быть одинаковыми для всех методов. Предложенный v2-конфиг расширяет их до `train:12, tune:4, select:4, test:8`; это верхние лимиты на доступные подходящие дни, а не гарантия наличия всех дней у каждого пользователя. Даже сохранение меньших v1-бюджетов давало бы приблизительно девятикратное увеличение обучающей когорты. Изменение лимитов допускается до окончательной фиксации по результатам **ресурсного пилота**, без просмотра confirmation-outcome. Число пользователей полезнее для пользовательского интервала, дополнительные дни — для точности внутри пользователя.

Точная временная доступность сохраняется:

```text
listen.available_at = timestamp + ceil(track_length_seconds * played_ratio_pct / 100) + 5
other.available_at  = timestamp + 5
cutoff(query_day)    = (query_day - 1) * 86400
history             = events with available_at < cutoff
```

Доля выше 100% не обрезается при расчёте задержки. Для дневных агрегатов эквивалентна строгая граница `available_day < query_day - 1`. Для нейросети нужно применить **ту же** границу: нельзя предоставлять ей внутридневную историю, когда baseline видит только snapshot.

Train/tune/select-target допускается только если его inferred `available_at` предшествует началу следующего периода; purge выполняется до выбора supervised-дней. Данные истории не удаляются — меняется только eligibility размеченного примера.

Глобальная временная граница предотвращает обучение на более поздних событиях при прогнозе ранних targets; локальный leave-last-out по каждому пользователю этого не гарантирует. Подбор временного target также меняет смысл оценки. Это мотивировано [Ji et al.](https://arxiv.org/abs/2010.11060) и [Time to Split](https://arxiv.org/abs/2507.16289).

## 3. Обновляемая история и запечатанные targets

Зафиксировать prequential-режим: веса модели неизменны, но доступные события предыдущих тестовых дней могут обновлять историю следующих дней. Это разрешено и одинаково для всех методов. Замороженная на дне 210 история была бы другим экспериментом.

Практический барьер против просмотра теста:

- Обучающие инструменты получают только train и development targets.
- Confirmation-query manifest содержит IDs, день, признаки/контекст и порядок строк, но не target, долю успешных запусков, mixed-группы или сравнительные scores.
- Confirmation-target сохраняется отдельно; до окончательного lock можно знать его хеш и размер файла, а не частоты классов и метрики.
- До открытия labels должны быть завершены все финальные checkpoint и сохранены вероятности всех заранее указанных моделей.
- Evaluator проверяет конфиг, исходники, ID-разделение, порядок строк, checkpoint и prediction hashes, затем один раз открывает labels и записывает сравнение.

Это **процедурная**, а не криптографическая независимость: исходный multi-event parquet содержит outcomes, а causal history builder обязан использовать уже известные прошлые ответы. Нельзя заявлять, что никто технически не имел доступа к данным; следует заявлять, что pipeline выбора не читает confirmation targets и аудитирует разрешённые срезы.

Тесты должны изменять текущие/будущие outcome и проверять неизменность более раннего контекста; включать равенство cutoff, replay >100%, delayed feedback через границу этапа, неизвестные ID и пустую историю.

## 4. Информационная справедливость

Manual и AutoFE используют события всех новых пользователей для глобальной популярности и истории откликов. Нейросеть только над собственной последовательностью не получает эквивалентного глобального состояния после train. Это было бы сравнение разных источников информации, а не только представлений.

Рекомендуется **HistoryGlobal**: необработанная собственная история плюс фиксированные глобальные marginal-признаки, общие с baseline. Для полного совпадения всех непрямо персональных manual-сигналов их **37**, а не 22:

- `global_positive_prior`: 1;
- по item/artist/album: по 11 столбцов — count/rate в окнах 7, 30 и all, recency, historical mean ratio, organic share, likes, dislikes: 33;
- три marginal-тренда 7/30: 3.

Категории user/item/artist/album кодируются обучаемыми представлениями. Собственные user/pair-агрегаты не подаются primary history-модели: она должна извлекать их аналог из последовательности. Если реализовано только 22 глобальных столбца, это надо назвать дополнительным сжатием информации: отсутствуют ещё 15 доступных baseline-сигналов.

Даже 37 столбцов совпадают с глобальным состоянием **manual**, а не со всеми возможными глобальными AutoFE-ядрами. Выбранные AutoFE-группы добавляют population-level окна/decay для item/artist/album; собственная история пользователя не позволяет их восстановить. Поэтому корректное описание простого варианта — общие фиксированные marginal-признаки с дополнительным сжатием global state у history-модели, а не строго одинаковое количество глобальной информации. Альтернативы до фиксации протокола: передавать выбранные глобальные AutoFE-признаки обоим методам (тогда history-модель условна на AutoFE-поиск) либо ограничить новые AutoFE-группы user/pair-отношениями. Выбор должен быть явным и не меняться по confirmation-метрикам.

Сырые последовательности ограниченной длины — тоже сжатие. Сохранение всех исходных событий не означает, что нейросеть увидела всю историю. Предложенная многомасштабная память содержит до 256 последних и 256 более старых событий; выбор старых токенов должен быть фиксированным и не зависеть от текущего outcome. Надо явно сообщить количество/долю доступных событий, представленных модели, и не интерпретировать неудачу как доказательство непригодности всех sequence-моделей. Увеличенная длина контекста полезна как заранее заданная абляция при достаточном бюджете.

ID-vocabulary строить по train-доступным данным либо использовать фиксированное hashing. Фитирование словаря частот по всем будущим событиям недопустимо без явного transductive-допущения. Exact-match gates должны сравнивать исходные IDs, а не hash buckets; коллизия embedding не должна становиться ложным совпадением объекта.

## 5. Сравниваемые методы и бюджет

Рекомендуемый минимальный набор:

| Метод | Назначение |
|---|---|
| Manual CatBoost | Сильная точка сравнения |
| AutoFE, matched backbone | Отбор дополнительных групп при тех же CatBoost-параметрах и числе деревьев, что у Manual |
| All Auto, независимо настроенный | Контроль всей процедуры с собственным подбором; не чистая абляция признаков |
| HistoryGlobal | Primary модель истории с тем же доступным глобальным состоянием |
| Pure History | Контроль влияния глобальной информации; возможен один фиксированный seed |
| История без contextual encoder | Проверка вклада encoder при тех же embedding/входах; возможен один seed |

Matched-backbone AutoFE устраняет confound v1, где одновременно менялись признаки, глубина и число деревьев. Для первичного сравнения HistoryGlobal–AutoFE выбранный AutoFE остаётся полноценной процедурой; независимую all-auto настройку нельзя после теста объявлять новым победителем процедуры отбора.

Для основных семейств — три заранее заданных seed, например прежние `[17,29,43]`, и среднее вероятностей. Односидовые абляции сравниваются с соответствующим одиночным seed основной модели, а не только с трёхсидовым ансамблем.

Равное число trials не означает равные FLOPs или wall time. Нужны оба описания: заданное число конфигураций/эпох, фактическое CPU/GPU-время, peak RSS/VRAM, preprocessing, контекстный cache, inference и размер checkpoint. Нельзя выдавать общий GPU-budget за равный budget всего исследования, если AutoFE использует дополнительный CPU-search.

Нейросетевой grid может включать заранее заданный pairwise-компонент с весом 0 или 0.1; выбирать его нужно на development по зафиксированному критерию. Это свойство сравниваемой процедуры, а не одинаковая с CatBoost функция обучения. В общей для user-day реализации BCE должен агрегироваться по строкам, а не как среднее средних групп. Все кандидаты дня сохраняются; при нехватке памяти следует разбить query-head на microbatches с тем же контекстом вместо изменения набора кандидатов.

После ресурсного пилота допускается уменьшить batch с gradient accumulation, сохраняя effective batch и архитектуру. Такие изменения выбираются по памяти/throughput до confirmation, фиксируются и не зависят от итогового качества.

## 6. Random-control без повторения ошибки v1

Сначала фиксируется RNG-seed. После выбора числа групп `K` взять **три разных равномерных подмножества размера K** из конечного пространства групп, без возвращения. Если возможных подмножеств меньше трёх, перечислить их все. Выбранный AutoFE-поднабор не исключать: совпадение остаётся допустимым наблюдением, а не поводом менять seed.

Распределение условно на K; буквальное построение подмножеств до знания K невозможно, но заранее фиксированный алгоритм и seed предотвращают подбор контроля по score. Дубликаты одинаковых спецификаций можно вычислять один раз, указывая число логических и реально обученных конфигураций.

Три контроля дают проверку здравого смысла и не являются точной оценкой распределения всех случайных поисков. Нельзя уверенно заявлять superiority селектора лишь потому, что он победил все три.

## 7. Основная гипотеза и интервалы

Предлагаемая одна primary-проверка:

```text
ΔLL = row-weighted LogLoss(HistoryGlobal ensemble)
      - row-weighted LogLoss(selected AutoFE ensemble)
```

Отрицательное значение благоприятно для HistoryGlobal. Парный bootstrap по confirmation-пользователям, 5000 повторов, фиксированный seed; исходные пользовательские блоки и веса строк сохраняются. Основной 95% интервал относится к одной заранее выбранной паре. ROC-AUC, Brier, AP, user-macro LogLoss, mixed user-day NDCG/Recall и остальные модели — вторичные сравнения, без скрытого изменения первичной метрики.

Победа по LogLoss не даёт автоматической победы по ранжированию. Для общего утверждения «качество рекомендаций улучшилось без потери ranking» нужен заранее обоснованный критерий по обеим метрикам; отсутствие значимого вреда не доказывает non-inferiority. Без продуктового допустимого margin лучше честно сообщать trade-off.

NDCG по фактически проигранным трекам остаётся условным ретроспективным ranking, не full-catalog retrieval и не оценкой смены policy. Mixed-группы определяются только evaluator после открытия labels; их доля и число покрытых пользователей сообщаются явно.

Пользовательский bootstrap условен на уже обученных моделях и этом временном периоде. Он не включает повторный подбор, переобучение или неопределённость нового календарного режима. Общие объекты и временные shocks создают межпользовательскую зависимость; классическая проблема crossed recommender data обсуждается в [Owen, The Pigeonhole Bootstrap](https://artowen.su.domains/reports/pbs2.pdf). Полезная чувствительность — график парной разницы по дням и отдельно заранее описанное resampling по пользователям и временным блокам. Такой анализ нельзя представлять как автоматически точный интервал для всех видов зависимости.

### Приблизительная точность: почему 9000 лучше 5000

В v1 половина ширины интервала selected AutoFE–Manual равна примерно 0.0029275 при 784 пользователях с тестовыми строками. Используя только для планирования нормальную аппроксимацию и масштабирование standard error как `1/sqrt(N)`:

| Новых confirmation-ID | Ожидаемо с тестовыми строками при v1 coverage | Половина ширины 95% CI | Мощность для абсолютного эффекта 0.001623 |
|---|---:|---:|---:|
| 4000 | 3136 | ~0.00146 | ~58% |
| 8000 | 6272 | ~0.00104 | ~87% |

Это не расчёт гарантированной мощности нейросети. Эффект v1 относится к другой паре методов; variance, активность, сэмплирование дней и policy могут измениться. Асимметричный percentile-CI лишь грубо заменён нормальным. При общей временной/объектной зависимости точность может быть хуже. Новый реальный эффект может быть как больше, так и меньше выбранного ориентирного значения.

### Устойчивость выбора без новых GPU-fit

Сохранённые development-прогнозы кандидатов позволяют дополнительно пересэмплировать development-пользователей и посчитать частоту выбора окон/конфигураций. Это диагностика winner's curse и чувствительности селектора, а не новый критерий выбора и не замена confirmation. Частоты можно получить без переобучения; они условны на уже обученных candidate-моделях.

## 8. Технические условия завершения

V2 следует реализовать в отдельном namespace, например `src/recsys_history_v2/`. V1 `source_fingerprint()` перечисляет все `.py` своего пакета, поэтому даже добавление нового модуля в `src/recsys_research/` нарушило бы прежнюю цепочку аудита. Старые source/конфиги/отчёт и checkpoint остаются без изменений.

Перед confirmation должны проходить проверки:

- нет пересечений old/dev/confirmation-ID; train покрывает только новую когорту;
- все методы получают одинаковые query IDs, targets и строгий availability cutoff;
- vocab/normalization/scaling fit только на разрешённом train;
- empty-history/missing-ID/padding дают конечные вероятности, градиенты не NaN;
- event order/padding/current outcome не меняют запрещённым образом результаты;
- exact-ID gates не используют метку и не срабатывают по hash-коллизии;
- эпохи/гиперпараметры/семейства/seeds и random-subsets записаны до test;
- все checkpoint и prediction hashes готовы до открытия confirmation labels;
- независимый пересчёт метрик, tie-aware NDCG и reload-checks воспроизводят итог.

Одна H100 удобна для sequence-training; CPU-подготовка агрегатов остаётся отдельным ограничением. Практичный remote host: 1×H100, предпочтительно 128 GiB RAM, минимум порядка 64 GiB при аккуратном потоковом preprocessing, 50 GB свободного SSD. Архитектура небольшой history-модели не требует именно H100 теоретически; текущий Mac с 8 GB RAM и малым свободным диском неудобен для полного 43M-event сравнения. Wall-time следует оценивать по реальному pilot-throughput, а не обещать заранее.
